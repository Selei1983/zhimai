# Web 与浏览器插件产品方案

## 产品形态判断

知脉建议采用三阶段产品形态：

1. Web 应用  
   承担核心整理、编辑、知识库浏览和账户数据管理。

2. 浏览器插件  
   承担网页阅读场景下的快速收集，把内容送回 Web 收集箱。

3. 桌面客户端  
   后续基于 Web 能力封装，增强本地文件、快捷键、离线和隐私能力。

这个顺序比较稳，因为知脉的核心难点不是客户端形态，而是知识重构流程是否成立。

## 产品总定位

知脉是一个 AI 原生的个人 Wiki 系统。

用户在日常阅读和工作中把碎片内容交给知脉，知脉负责理解、拆解、重构、关联，并沉淀为长期可复用的个人知识库。

## 端的分工

### Web 应用

Web 是主产品。

它负责：

- 收集箱
- AI 整理台
- Wiki 页面生成
- Wiki 页面编辑
- 知识库浏览
- 标签与关联管理
- 用户账户与同步
- AI 使用记录

用户主要在 Web 里完成确认、编辑和复盘。

### 浏览器插件

浏览器插件是轻量入口。

它负责：

- 保存当前网页
- 保存选中文本
- 保存网页标题和 URL
- 保存用户临时想法
- 发送到 Web 收集箱
- 显示是否已同步

插件不做重编辑，不做复杂知识库浏览。

### 桌面客户端

客户端是第三阶段形态。

它负责增强：

- 本地 Markdown 文件读写
- 系统级快捷键
- 离线草稿
- 本地隐私模式
- 更顺滑的长期写作体验

客户端不应另起一套产品逻辑，而应复用 Web 的核心页面和服务。

## Web 应用设计

### 1. 首页

登录后首页不做营销页，直接进入工作台。

首页应该展示：

- 快速输入框
- 最近收集
- 待整理内容
- 最近更新的 Wiki 页面
- 今日新增知识

首页的目标是让用户马上开始输入，而不是阅读产品说明。

### 2. 收集箱

收集箱保存所有还没有完成知识化的内容。

内容来源：

- Web 输入
- 浏览器插件
- 手动粘贴
- 后续的文件导入

列表字段：

- 标题
- 来源
- 摘要
- 状态
- 创建时间
- 推荐动作

状态：

- 未整理
- 已分析
- 待确认
- 已写入 Wiki
- 已忽略

### 3. 整理台

整理台是核心界面。

建议采用三栏布局：

- 左栏：原始内容
- 中栏：AI 判断
- 右栏：Wiki 草稿

AI 判断包括：

- 内容类型
- 主题
- 核心观点
- 推荐动作
- 推荐关联页面
- 风险提示

用户操作：

- 接受草稿
- 修改草稿
- 新建 Wiki 页面
- 补充已有页面
- 拆分成多个页面
- 暂存
- 忽略

### 4. 知识库

知识库是正式沉淀区。

页面列表支持：

- 搜索
- 标签筛选
- 类型筛选
- 最近更新排序
- 关联数量排序

页面详情支持：

- Markdown 阅读
- Markdown 编辑
- 相关页面
- 来源材料
- 更新记录
- 继续补充材料

### 5. 关联视图

第一版可以先做轻量关联视图，不急着做复杂图谱。

页面详情中展示：

- 上位主题
- 相关概念
- 对比页面
- 案例页面
- 补充页面

第二阶段再做真正的脉图。

## 浏览器插件设计

### 插件主场景

用户在网页上看到一段有价值的内容，希望快速送进知脉。

插件应支持三种收集方式：

1. 选中文本后保存
2. 保存当前网页
3. 保存网页并附加自己的想法

### 插件弹窗

弹窗结构：

- 当前网页标题
- 当前网页 URL
- 选中文本预览
- 用户备注输入框
- 标签建议
- 保存按钮

保存后显示：

- 已发送到收集箱
- 打开整理台
- 稍后整理

### 右键菜单

右键菜单提供：

- 保存到知脉
- 保存选中文本到知脉
- 用知脉整理这段内容

### 插件边界

第一版插件不做：

- 页面全文抓取
- 页面内容重写
- 网页内浮层编辑器
- 本地知识库搜索
- 离线同步

插件越轻，越容易稳定发布。

## 数据流

### Web 手动输入

```text
用户输入 -> 收集箱 -> AI 分析 -> 整理台 -> 用户确认 -> Wiki 页面
```

### 插件收集

```text
网页选中内容 -> 插件 -> Web API -> 收集箱 -> AI 分析 -> 整理台 -> 用户确认 -> Wiki 页面
```

### 后续客户端

```text
客户端输入 -> 本地草稿 -> Web 同步 -> 整理台 -> Wiki 页面 -> 本地 Markdown 同步
```

## 核心数据对象

### Capture

一次收集行为。

字段：

- id
- user_id
- source_type
- source_title
- source_url
- selected_text
- note
- tags
- created_at
- status

### ProcessingResult

AI 整理结果。

字段：

- capture_id
- summary
- content_type
- topics
- suggested_action
- suggested_title
- key_points
- wiki_draft
- related_pages
- quality_notes

### WikiPage

正式知识页面。

字段：

- id
- user_id
- title
- type
- content_markdown
- tags
- sources
- related_pages
- created_at
- updated_at

## MVP 功能清单

### Web MVP 必做

- 登录
- 快速输入
- 收集箱列表
- AI 整理
- 整理台预览
- Markdown 草稿编辑
- 确认写入 Wiki
- Wiki 页面列表
- Wiki 页面详情
- 标签

### 浏览器插件 MVP 必做

- 登录授权
- 保存当前页面
- 保存选中文本
- 添加备注
- 发送到收集箱
- 打开 Web 整理台

### 暂缓

- 多人协作
- 公开发布
- 图谱动画
- 移动端 App
- 完整离线
- 自动全文抓取
- 复杂网页标注

## 第一版产品判断标准

第一版是否成功，主要看三件事：

1. 用户是否愿意持续把内容丢进来
2. AI 生成的 Wiki 草稿是否值得保留
3. 浏览器插件是否明显降低收集成本

如果这三件事成立，再做客户端才有意义。

## 推荐技术方向

先用 Web 技术做统一底座：

- Web 前端：整理台、知识库、页面编辑
- 后端 API：收集、整理、写入、搜索
- 浏览器插件：调用同一套收集 API
- 客户端：后续用 Web 容器封装

这样可以避免三端重复开发。
